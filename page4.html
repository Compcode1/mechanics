The Global Standard (ReAct) Interleaving reasoning and acting to interface with external environments and halt error propagation.
Plain Talk Translation (The Clinical Feedback Loop) Instead of asking the AI to write a massive script in one blind guess, we force a disciplined cycle: synthesize payload → execute in local terminal → verify live directory/telemetry state → patch any friction with a full state re-sync.
2. Bounded Autonomy
The Global Standard (OWASP LLM08) Neutralizing excessive functionality, unconstrained permissions, and dangerous downstream autonomy.
Plain Talk Translation (The Digital Straitjacket) OWASP LLM08 warns against "Excessive Agency." We solve it by trapping the AI inside a deterministic state machine where its code cannot delete infrastructure and its identities are strictly locked to a single Data-Plane asset.

The Global Standard (NIST AI RMF) Establishing the "Govern" function for transparent risk tolerance and explicit human accountability.
Plain Talk Translation (The Two-Key Launch System) The AI is completely air-gapped from your live cloud. It writes the code and terminal runbooks, but a hard [STRICT HALT] drops at every phase so nothing touches Azure without the human Architect turning the key.
4. Cognitive Circuit Breaking
The Global Standard (Hallucination Research) Combating probabilistic drift and the generation of plausible yet nonfactual outputs over sustained context windows.
Plain Talk Translation (The 4-Iteration Kill-Switch) When an LLM gets stuck on a bug for too many turns, its attention dilutes and it starts guessing wildly. At Iteration 4, our breaker physically forbids code generation, calculates a Success Probability (%), and hands the strategic decision back to you.

Column 1: Identity Core (The Central Authority)
This coordinate never changes because it is the sovereign root of trust for the entire Microsoft cloud ecosystem.
Microsoft Entra ID (formerly Azure Active Directory) ROOT IDENTITY PROVIDER (IdP)
Plain Talk: Think of Entra ID as the Federal Passport Agency and Border Control for your entire company. Every human employee and every automated machine workload must be registered here. In our architecture, Entra ID holds the App Registration (global blueprint), the Service Principal (local security officer), and the Federated Identity Credential (the OIDC customs rulebook that inspects incoming tokens from your Execution Agent and issues temporary 60-minute Azure access badges).
Column 2: Execution Agent (Who Is Knocking at the Door?)
The Execution Agent is the external automation platform or container cluster that needs passwordless access into Azure. Selecting a different agent completely changes the Issuer URL, the Subject Claim format in Phase 2, and the Validation YAML in Phase 4.
1. Azure Kubernetes Service (AKS) CONTAINER WORKLOAD IDENTITY
Plain Talk: Whereas GitHub, Azure DevOps, and GitLab are CI/CD build pipelines, AKS is a live fleet of containerized microservice applications running inside Azure. When a pod (container) inside AKS needs to read a secret from Key Vault, we don't want to bake passwords into the container image.
How It Works in Our Machine: AKS has its own built-in OIDC token issuer URL. Each Kubernetes pod runs under a specific Service Account inside a Namespace. Its Subject Claim looks like: system:serviceaccount:<namespace>:<service_account_name>. In Phase 4, instead of running a CI/CD pipeline, we deploy a Kubernetes Pod manifest (kubectl apply -f validate-pod.yaml) to prove the container can trade its Kubernetes token for an Azure Data-Plane token.
2. GitHub Actions CI/CD AUTOMATION RUNNER
Plain Talk: GitHub's built-in automation engine that builds, tests, and deploys code whenever you push to a repository.
How It Works in Our Machine: GitHub's OIDC Issuer URL is https://token.actions.githubusercontent.com. Because repository names can be renamed or spoofed, our State Machine (Rule 24) enforces strict CompCode1 casing and extracts the hidden, immutable numeric Node IDs (`owner_id` and `repo_id`) in Phase 2 so the Subject Claim (`repo:CompCode1@<id>/<repo>@<id>:ref:refs/heads/main`) is mathematically bulletproof against AADSTS700213 drops.
3. Azure DevOps (ADO) ENTERPRISE MICROSOFT CI/CD
Plain Talk: Microsoft's enterprise project management and CI/CD pipeline suite (`azure-pipelines.yml`), heavily used by large corporations.
How It Works in Our Machine: ADO connects to Azure via a construct called a Service Connection. Unlike GitHub (where you construct the Subject Claim from repo paths), ADO generates an opaque, backend GUID string for its OIDC Issuer and Subject Claim. In Phase 2, our State Machine generates a specialized REST API extraction script to pull those exact opaque ADO federation strings before synthesizing Phase 3.
4. GitLab CI DEVSECOPS PIPELINE RUNNER
Plain Talk: A major competitor to GitHub Actions (`.gitlab-ci.yml`), widely used in security-conscious enterprises.
How It Works in Our Machine: GitLab's OIDC Issuer is https://gitlab.com, and its Subject Claim is structured around the exact group/project namespace path and branch: project_path:<group>/<project>:ref_type:branch:ref:<branch_name>. In Phase 4, the runner mints a `GITLAB_OIDC_TOKEN` JWT and trades it directly with Entra ID via `az login --service-principal --federated-token`.
Column 3: Infrastructure State (What Is Already on the Ground?)
This toggle tells the State Machine whether we are walking onto an empty construction lot or renovating a live hospital wing—triggering Rule 3 (Destructive State Prevention).
1. Brownfield (Existing Infrastructure) READ-ONLY LOOKUPS (DATA BLOCKS)
Plain Talk: In real urban planning, a "brownfield" site already has existing buildings and utility lines on it. In cloud engineering, Brownfield means the Resource Group, Key Vault, or AKS cluster already exists in production.
How It Works in Our Machine: If you select Brownfield, the AI is strictly forbidden from creating a new vault or overwriting the existing one. Instead, it generates read-only data blocks (e.g., data "azurerm_key_vault" "existing") to safely look up the existing asset's Resource ID and attach the new Zero Trust identity to it without disturbing live traffic.
2. Greenfield (Net-New Infrastructure) CREATE + PREVENT_DESTROY LOCKS
Plain Talk: A "greenfield" site is an untouched field of grass—we are building the entire environment from scratch.
How It Works in Our Machine: When you select Greenfield, the AI writes resource blocks to provision the net-new Resource Group, Target Asset (Key Vault/Storage/Cosmos), and Entra ID objects all at once—and automatically stamps lifecycle { prevent_destroy = true } onto the critical resources so future runs can never accidentally delete them.
Column 4: Data-Plane Asset (Which Safety Deposit Box Are We Opening?)
This selects the specific high-value cloud asset our workload needs to read from. Under Rule 4 (PoLP), this choice dictates the exact surgical Data-Plane RBAC role assigned at Gate 4 and the exact API read test run in Phase 4.
1. Azure Key Vault ROLE: KEY VAULT SECRETS USER
Plain Talk: A hardware-backed digital safe used to store API keys, certificates, and connection strings.
How It Works in Our Machine: We enable enable_rbac_authorization = true on the vault, ban broad Control-Plane roles, and assign the surgical Key Vault Secrets User role—which allows the workload to read secret values inside that single vault, but forbids it from deleting secrets, changing access policies, or deleting the vault itself.
2. Azure Storage Account (Blob Storage) ROLE: STORAGE BLOB DATA READER
Plain Talk: Massive, enterprise file warehousing used to store unstructured data like AI training datasets, backups, logs, and artifacts.
How It Works in Our Machine: Control-plane permissions don't let you read files safely; we scope the workload identity strictly to the Data Plane using Storage Blob Data Reader (or Contributor if writing artifacts) on that specific storage container, and validate it in Phase 4 using az storage blob list --auth-mode login.
3. Azure SQL / Cosmos DB (NoSQL) ROLE: COSMOS DB BUILT-IN DATA READER
Plain Talk: High-speed, globally distributed enterprise databases that hold live customer records and application state.
How It Works in Our Machine: Instead of using connection strings with embedded master passwords (which get leaked constantly), we bind the federated workload identity to Cosmos DB's native Data-Plane RBAC role definition (00000000-0000-0000-0000-000000000001 / Built-in Data Reader), proving passwordless database authentication.
Column 5: IaC Payload (Which Language Builds the Blueprint?)
Infrastructure as Code (IaC) means we never click around in web portals to build security—we write code files that compile the architecture deterministically. Each of these three languages has a distinct strength in an interview.
1. Terraform (HCL - HashiCorp Configuration Language) MULTI-CLOUD INDUSTRY STANDARD (main.tf)
Plain Talk: The gold standard across enterprise cloud engineering because it speaks to everything (`azurerm` for Azure resources, `azuread` for Entra ID, and `time` for sleep buffers) inside a single unified file (main.tf) backed by a state file (terraform.tfstate).
Key Quirk You Mastered: Our directive (Rule 23 & 27) automatically handles remote state backend protection, maps azuread_named_location via .id, and injects a 30-second time_sleep resource to absorb Microsoft Graph eventual consistency race conditions.
2. Azure Bicep MICROSOFT NATIVE DECLARATIVE (main.bicep)
Plain Talk: Microsoft's own domain-specific language created as a cleaner replacement for old JSON ARM templates. Its biggest advantage is that it is stateless—Azure itself stores the state in the cloud, so there is no local terraform.tfstate file to lose or corrupt.
Key Quirk You Mastered: By enabling the Microsoft Graph Bicep extension (`extension microsoftGraphV1`), our engine compiles both Entra ID federated identities and Azure Data-Plane resources inside a single native main.bicep deployment.
3. PowerShell REST API (Microsoft Graph & ARM) ZERO-DEPENDENCY IMPERATIVE (deploy.ps1)
Plain Talk: Instead of using a third-party compiler like Terraform or Bicep, this sends raw HTTPS JSON requests (Invoke-RestMethod) directly to the Microsoft Graph API (`graph.microsoft.com`) and Azure Resource Manager endpoints.
Key Quirk You Mastered: Under Rule 29 & Rule 30, our engine strictly uses native Graph JSON schemas (never bleeding Terraform attribute names into JSON) and automatically decouples ARM role assignments when local CLI tokens drop tenant MFA claims.
